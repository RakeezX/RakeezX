# سجل الترحيلات — MADAR Z

آخر تحديث: 2026-08-16 · يوثّق كل ترحيل نُفّذ على البيانات، وقواعد الترحيل القادمة.

---

## قاعدتان تحكمان كل ترحيل

1. **نسخة احتياطية إجبارية قبل أي ترحيل يمس مفتاحًا.**
2. **الترحيل كله في معاملة واحدة** — إن فشل أي سجل تراجع كل شيء، ولا تبقى حالة جزئية.
   البنية موجودة: `db.applyBatch` و `db.writeAll`.

## `SCHEMA_VERSION` المحلي

| الإصدار | ما تغيّر | الحالة |
|---|---|---|
| ١ | المخطط الأول: `classes` · `students.classId` · حضور بمفتاح اليوم | تاريخي |
| ٢ | **معرّفات مشتقة** للدرجات والحضور، ودمج المكرر | ✅ نُفّذ |
| ٣ | **النموذج الجديد**: شعب · إسنادات · انتسابات · حصص · تقويم · منهج | ✅ نُفّذ |
| ٤ | **فصل الإعدادات** إلى `profile` و `device`، وملفات التوقيت | ✅ نُفّذ |

`DB_VERSION` لقاعدة IndexedDB: **٢**.

## ترحيل ١ → ٢: المعرّفات المشتقة

**السبب:** جهازان دون إنترنت كانا يخلقان سجلَّي درجة لنفس (طالب، بند). قِيس فعلًا:
الشاشة تعرض ٩ والمعلّم يرصد ٥ — إفساد صامت.

**ما تغيّر:** `sc:{studentId}:{itemId}` و `at:{studentId}:{classId}:{date}`.

**النتيجة:** درجتان مكررتان ← واحدة (الأحدث ختمًا) · سجلا حضور مكرران ← واحد ·
سجل الأحداث لم يُمسّ.

---

## ترحيل ٢ → ٣: النموذج الجديد

**السبب:** `classes` كان يخلط الشعبة بالإسناد بالمادة، والطالب مربوطًا بفصل واحد للأبد،
والحضور باليوم لا بالحصة.

| # | من | إلى |
|---|---|---|
| ١ | `term.year` نص حر | `years` بمعرّف مشتق |
| ٢ | `terms` | + `yearId` · `index` · `status` |
| ٣ | `class.subject` نص | `subjects` بمعرّف مشتق |
| ٤ | `classes` | `sections` (تفكيك `٤/أ` إلى صف ورمز) |
| ٥ | `classes` | `teachings` — خريطة ١:١ |
| ٦ | `items.classId` | `items.teachingId` |
| ٧ | `scores` | **بلا تغيير** |
| ٨ | `students.classId/rollNo` | `enrollments` + `students.status` |
| ٩ | `(classId, date)` في الحضور | `sessions` بـ `period=1`, `status='held'` |
| ١٠ | `at:{sid}:{cid}:{date}` | `at:{sid}:{sessionId}` |
| ١١ | `logs.classId` | `logs.teachingId` + `sessionId` |

**النتيجة المقيسة:** ٢ فصل ← ٢ شعبة و٢ إسناد · ٢٥ طالبًا بلا `classId` + ٢٥ انتسابًا ·
١٢٥ حضورًا ← ٥ حصص و١٢٥ حضورًا بمفتاح الحصة · **٧٥ درجة بلا أي تغيير**.

**تحذيرات موثّقة** بدل المرور الصامت:

```
تواريخ بداية الفصول الدراسية ونهايتها غير معروفة — تحتاج إدخالًا يدويًا.
رُحّل N يومًا من الحضور إلى حصص برقم ١ — المخطط القديم لم يكن يسجّل رقم الحصة.
اسم الفصل «…» لم يُفكَّك إلى صف ورمز شعبة — استُعمل الاسم كاملًا رمزًا.
تعذّر تحليل السنة «…» — أُنشئت سنة تحتاج تصحيحًا يدويًا.
```

## ترحيل ٣ → ٤: فصل الإعدادات

**السبب:** سجل إعدادات واحد يخلط بيانات المعلّم بإعدادات الجهاز. دمج نسخة احتياطية كان
يقفز بالمعلّم إلى فصل دراسي غير الذي يعمل عليه — لأن سجلًا واحدًا لا يمكن دمج نصفه.

**ما تغيّر:** `meta` ← `profile` (يُصدَّر ويُدمج) + `device` (لا يغادر الجهاز)،
وأُنشئت `timeProfiles` بأربعة ملفات مبدئية.

`splitMetaIfNeeded()` يوزّع الحقول ثم يفرّغ المخزن القديم. لا يُفقد حقل واحد.

---

## ترحيل الهوية: قاعدة بيانات مختلفة

تغيير اسم المنتج غيّر `DB_NAME` — **وهذه قاعدة أخرى تمامًا لا حقل**.

```
١. يفتح التطبيق قاعدته الجديدة (فارغة)
٢. يقرأ القاعدة السابقة دون إنشائها إن لم تكن موجودة
٣. يحوّلها إلى النموذج الجديد
٤. يكتبها في معاملة واحدة
٥. **لا يحذف القاعدة القديمة** — تبقى شبكة أمان
```

**معرّفان قديمان باقيان عمدًا** في `db.js` و `export.js`: جسر باتجاه واحد يُقرأ منه
ولا يُكتب إليه. حذفهما ممكن بعد أن تنتقل كل الأجهزة وتُستورد كل النسخ القديمة.

## `BACKUP_VERSION`

| الإصدار | المحتوى |
|---|---|
| ١ | المخطط القديم — **يُقبل للاستيراد ويُرحَّل، ولا يُكتب أبدًا** |
| ٢ | النموذج الجديد قبل فصل الإعدادات |
| ٣ | الحالي — `profile` بدل `meta`، و`device` مستبعد تمامًا |

**استيراد نسخة قديمة يمر بنفس دالة الترحيل قبل الكتابة**، فلا تدخل القاعدة سجلات
بشكل قديم. مُختبر: نسخة قديمة استُوردت، وأُنشئت لها شعبة وإسناد وحصة، ولم يبقَ سجل
بالشكل القديم.

## ترحيلات Supabase

`supabase/migrations/` — مرقّمة، والقاعدة قابلة لإعادة البناء منها وحدها:

| الملف | المحتوى | الحالة |
|---|---|---|
| `0001_core_schema.sql` | ١٩ جدولًا · مفاتيح · علاقات · قيود | **مكتوب، لم يُنفَّذ** |
| `0002_indexes_triggers_rls.sql` | فهارس · أختام · RLS · صلاحيات | **مكتوب، لم يُنفَّذ** |

### قواعد ترحيلات الخادم

1. **إضافية فقط** — أعمدة جديدة بقيم افتراضية، لا حذف ولا إعادة تسمية. فجهاز على
   مخطط قديم يواصل العمل بلا كسر.
2. **`schemaVersion` يُرسل مع كل مزامنة.** الأقدم من الحد الأدنى يُرفض برسالة
   «حدّث التطبيق» — **ولا تُمسح بياناته المحلية**.
3. **كل تغيير يمس مفتاحًا أساسيًا يتم قبل تشغيل المزامنة لا بعدها.** وهذا سبب تنفيذ
   الموجة الأولى محليًا أولًا: بعد المزامنة يصير الترحيل موزّعًا على أجهزة قد يبقى
   بعضها دون إنترنت أسابيع.
4. **لا تغييرات مباشرة من لوحة Supabase** تترك المخطط بلا تاريخ. كل تغيير ملف مرقّم.
