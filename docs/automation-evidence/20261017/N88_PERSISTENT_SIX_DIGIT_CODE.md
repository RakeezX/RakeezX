## Result and scope

The previous expiring, first-use-consumed invitation is replaced in the inert pilot modules by a persistent personal code. A student bookmarks a teacher-specific `/s/<random-public-namespace>` entry URL and enters **one six-ASCII-digit string**, including leading zeroes. There is no name/email/phone/student-ID field, global six-digit lookup, invitation fragment, automatic send, student Auth account or new paid provider.

Teacher selects a current verified enrollment from the server response, creates/rotates the code, manually copies/prints it for that verified student and dismisses its one-time display. The server cannot retrieve old plaintext; forgotten codes must be regenerated. It returns no old code in later teacher listings. Rotation reserves a fresh value, tombstones old verifier values, increments version and revokes all old sessions in one transaction. Revoke also disables the code and every session. Issuance failure rolls back instead of silently losing the previous credential.

## Code lifetime, sessions and security boundaries

- Code has **no timeout or first-login consumption**. Multiple independent sessions and returns work until rotate/revoke/membership termination. The 8-hour session can expire or be logged out without invalidating the code. The 30-minute local HTTP server lifetime is unrelated to code lifetime.
- `node:crypto.randomInt(0, 1000000)` generates codes. The repository serializes uniqueness/rotation/revocation/version binding. Verifiers are HMAC-SHA256 with domain + teacher namespace, using a newly generated, injected server-only 256-bit synthetic key. No committed server secret, plain SHA of PINs, raw-code persistence or old-code recovery.
- 256-bit random session values are stored server-side as hashes, delivered only through finite `__Secure-n88` HttpOnly/Secure/SameSite=Strict cookies scoped to `/api/n88/s/<namespace>`. Every read verifies namespace, owner/class/student/enrollment, membership revision/activity, current credential/version/revocation and session expiry. POST requires exact Origin + JSON + custom CSRF header, with no CORS path.
- Student code travels only in transient POST JSON. Forms clear before awaiting; no credentials in URLs/query/fragments/storage/analytics/logging. No-store/private, no-referrer, noindex/nofollow/noarchive headers are applied. Hash/query input is discarded, never treated as a credential. Async generations discard old student responses; page lifecycle/context changes clear rendered content. Teacher context-change re-verifies auth and clears old selections/code.
- `verifyTeacher` is a required server adapter for independently verified **current** auth/session. Supplied owner/student fields or editable metadata do not select authority. The fixture's teacher header maps fabricated identities only: it is deliberately not a hosted auth adapter.
- `verifyIngress` is a required trusted server adapter. The HTTP fixture uses the actual socket address, not supplied body/IP/forwarded headers. Future reverse proxies must strip untrusted forwarded values and authenticate their ingress identity; otherwise fail closed. No hosted proxy has been certified.
- Future canonical membership lifecycle must atomically revoke credentials/sessions when membership/student/class ends, increment a monotonic revision and never reuse an old membership generation on re-enrollment. ## Guessing budget and remaining risk

All claims, including varying codes/unknown namespaces, reserve budgets **before context or credential lookup** in the same serialized transaction. Fixed 15-minute windows: **6 attempts per server-verified client/IP, 30 per teacher context, 100 globally**. Before lookup, daily failed-attempt budgets also cap **60 per context, 500 globally per 24 hours**. Counts persist across 15-minute window changes in the fixture. Maximum 10,000 live budget keys; capacity exhaustion fails closed. A supplied-code-only limiter is not used.

Six digits give only one million possibilities. With one target credential, 60 distinct random daily failures correspond to about 0.006% daily guessing probability; the chance of reaching *any* student grows with the number of active codes (approximately attempts × active codes / 1,000,000 for small probabilities). Fixed-window boundaries permit bursts, and daily counters do not stop distributed targeted harassment. Tight context/global limits can deny legitimate students behind shared school NATs or during an attack. Those availability costs need measured hosting review, not silent threshold increases. Namespace knowledge is not authentication. Server-key compromise exposes low-entropy codes to enumeration; HMAC is not a claim of strong PIN entropy.

The supplied memory repository serializes ONE process and rolls back exceptions. Restart loses fixtures, credentials and budgets. It is **not durable or multi-instance proof**. The private-schema proposal records uniqueness/FKs/version binding, deny-by-default RLS/grants and required lock/admission/read/lifecycle contracts. A future durable repository/shared limiter must commit failed-admission counters (rather than rolling them back with a rejected login), maintain a bounded keyspace, and enforce canonical lifecycle/owner isolation across instances. Durable implementation, retention/key management, current teacher Auth, HTTPS/proxy and database/RLS verification are separate unrun hosted gates.
