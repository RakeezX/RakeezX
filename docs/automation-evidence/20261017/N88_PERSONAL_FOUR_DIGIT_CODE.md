## Implemented behavior and capacity

The server generates `String(randomInt(10000)).padStart(4, '0')`. Codes are strings, including `0000`, `0007` and repeated digits. There are **10,000 theoretical strings**, or 9,000 if a future policy forbids an initial zero (this implementation permits it). The teacher's own 303-student example is not a limit or hardcoded count. A public teacher page with four digits alone would make one random guess hit any of 303 active codes with probability **303/10000 = 3.03%**. That private-profile design is unapproved and is not implemented.

Each issuance atomically reserves a PIN verifier within the verified owner's single namespace, creates a separate 256-bit private student entry secret, revokes the previous credential and **all** its sessions, and increments the version. The repository's serializable transaction contract and SQL unique constraint prevent duplicate active PINs among that teacher's students. No sequential fallback or overwrite. Maximum **128** cryptographic candidate draws; collision/exhaustion fails generically and rolls back, preserving the prior credential/session.

Conservative existing tombstones reserve historical PINs too. Thus a teacher has at most 10,000 lifetime distinct PIN issuances in this proposal; random collision refusal can occur earlier, especially near capacity. No patterns are excluded. A future change to this reservation policy is separate work; no claim that every value is always assignable. This bounded behavior is explicit rather than an infinite loop or weakened randomness.

Teacher selects the current server-listed enrollment, creates/rotates the PIN/link, and manually shares both only after verifying that student over a trusted channel. No automatic message. Neither plaintext value is recoverable later; forgotten credentials require rotation. Rotation changes **both** link and PIN; revoke invalidates both and every session. Neither credential expires because time passed or first login occurred. Sessions retain their independent 8-hour expiry and logout; the same bookmarked link/PIN permits later sessions until rotation/revoke/membership termination.

## Exact private-link handling and threat boundary

The concrete route is **`https://<dedicated-origin>/s/<32-random-byte-base64url-secret>`**, a 43-character, 256-bit private bookmark credential. It is deliberately not a teacher namespace, enrollment ID, name or public student ID. The normal browser bookmark remains this same useful route across sessions/devices; it is not deleted and then falsely advertised as reusable. No fragment bootstrap, invitation timer, one-use link, public teacher+PIN lookup or browser-local bearer PIN is introduced.

The client addresses `/api/n88/s/<same-private-secret>/{claim,read,logout}`. The only form field is the four-digit PIN, sent in transient same-origin POST JSON with exact Origin, JSON content type and custom CSRF header; redirect is refused. The existing digit adapter normalizes Arabic/Persian digits before native form validation. The field clears before awaiting. Query/hash are discarded and never credentials; PINs never enter URLs, browser storage or logs.

Repository state stores only **server-keyed HMAC-SHA256 verifiers** of the entry secret and namespace/PIN; sessions store a hash of their independent 256-bit token and the entry verifier. It never stores the raw private entry secret or PIN. Login reserves trusted-client, private-context and global budgets before context/credential lookup, resolves the **exact entry verifier**, and compares only that credential's PIN verifier with a constant-time comparison. Another enrolled student's valid PIN cannot select/switch a profile. Public teacher namespaces and IDs fail. Session cookies are finite `__Secure-n88`, HttpOnly, Secure, SameSite=Strict, scoped to the exact private entry API path. Every read rechecks entry verifier, owner/class/student/enrollment, membership revision/activity, credential/version/revocation and session expiry, then reads only currently published tasks/progress. Default projection has no grades, private notes, attendance or classmates.

**Private-path tradeoff:** the secret intentionally remains in browser address/history/bookmarks (and can be copied/printed manually). Anyone obtaining it has the high-entropy part of the credential and can attempt that student's low-entropy PIN; someone obtaining both can impersonate that student. Shared devices, browser/bookmark sync, screenshots, compromised browser/origin/server or clipboard disclosure are outside the source pilot's protection. Rotation is the response to disclosure. A four-digit PIN is not strong standalone authentication.

Every pilot page/API/static response sends `Cache-Control: no-store, private`, `Referrer-Policy: no-referrer`, `X-Robots-Tag: noindex, nofollow, noarchive` and nosniff. The fixture has no analytics, third-party scripts or access logging. Production needs a dedicated HTTPS origin without unrelated scripts/Service Workers; disable/redact **raw private paths, cookies, request/response bodies, error URLs and tracing** at every CDN/proxy/server/monitoring layer **before** hosting. TLS protects transport, not the origin or its logs. This path design does not assert those external controls exist. It does not silently promote an ordinary public identifier to a credential.
