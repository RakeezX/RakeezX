# ركيز — شرط حفظ نوع التعليم والمسار بصورة صحيحة (تصميم V2)
**25 أكتوبر 2026 — تصميم معماري، وليس ترحيلًا منفذًا أو SQL معدّلًا.**

## لماذا لا نكتب حقولًا إضافية مباشرة؟
- `src/models.js:makeSection` يقبل حقولًا إضافية داخل السجل المحلي، لكن `src/lib/sync.js` يحول الشعب والإسنادات بخريطة حقول صريحة لا تتضمن البرنامج أو المسار أو نسخة المقرر. أي إضافة عشوائية قد تظهر محليًا ثم تختفي عند المزامنة/الاسترجاع.
- `src/lib/db.js` يعرف مخازن IndexedDB صريحة، ومزامنة `cloud.js` والإسنادات تستخدم هوية وكيل المالك ونسخة التخزين. لا يجوز حفظ «روضة» بوصفها `grade=13` أو الإدعاء أن حقولًا جديدة متزامنة دون ترحيل واختبار.
- فصل المدرسة واحد لكل مجموعة طلاب عبر السنة، بينما إسناد المادة مستقل لكل فصل دراسي. نوع التعليم/البرنامج/المرحلة/المستوى والمسار يُمثّل **بحد أدنى في سياق الشعبة**، وترتبط **نسخة مقرر** بكل إسناد مادة.

## الكيانات المقترحة — لم تُطبق في Supabase
### sectionCurriculumScopes
`{ ownerId, sectionId, yearId, programmeKey, stageKey, levelKey, trackKey?, sourceEdition, sourceRevision?, appliedAcademicYear?, reviewedAt?, deleted, updatedAt }`
- المفتاح الطبيعي: المالك + الشعبة + السنة؛ ينشأ سياق واحد فعال لنفس الشعبة، ولا يسمح بتغيير البرنامج دون ترحيل/مراجعة.
- يوفر دعم الصفوف 1–12 الحالية والروضة والمستويات التأهيلية/البرامج الخاصة؛ لا يفترض أن لكل سياق رقم صف 1–12.
- `appliedAcademicYear` لا يُسند 1448 افتراضيًا لمجرد وجود رقم الإصدار السادس.

### teachingCourseBindings
`{ ownerId, teachingId, sectionId, termId, subjectId, courseSourceKey, edition, sourcePage, reviewStatus, deleted, updatedAt }`
- يربط مادة المعلم المستخدمة فعليًا بالمقرر الرسمي الموافق لبرنامج الشعبة وصفها/مستواها ومسارها.
- لا يعيد توليد معرفات `section` أو `teaching` أو `subject` الحالية ولا يبدل سجل الطالب.
- المادة نفسها يمكن أن تُسند إلى فصول متعددة؛ الفصل الواحد يستوعب عدة مواد دون تكرار أسماء الطلاب.

## الترحيل المنتج لاحقًا — يجب أن يكون عبر بطاقة منتج مخوّلة
1. مراجعة حالة N36/N88/N44 والبطاقات المفتوحة وتثبيت نسخة `main` الفعلية. لا عامل نشر موازٍ.
2. التحقق من التصميم مع مخطط Supabase الحالي وقواعد RLS وFK، ووضع قيود المالك `owner_id` لكل سجل؛ `TO authenticated` وحده لا يكفي؛ وسياسات UPDATE تتطلب USING وWITH CHECK.
3. اختيار صيغة ترحيل مضافة (sidecar) للأعوام الحالية، دون إعادة كتابة جداول الطلاب أو الدرجات، مع حقول رفض السياق المتعارض.
4. إضافة المجموعات الجديدة إلى `src/lib/db.js` ومحول المزامنة وOutbox وRemote، والحذف الناعم وإيصال كل حدث، وفحص حسابين وأجهزة متعددة/انقطاع/استرجاع.
5. دمجها مع Backup/Restore وإقفال الفصل وأرشفة السنة قبل تفعيل أي مدخل في واجهة المستخدم.
6. **Backfill مراجَع**: الصفوف 1–12 لا تُفترض تعليمًا عامًا إذا كانت هناك إشارات فعلية للتحفيظ أو غيره. تحتاج شعبة قديمة غير معروفة «قيد المطابقة» بدل تصنيف خاطئ.
7. إطلاق طبقة قراءة مزدوجة (القديم والجديد) أولًا. الكتابة تكون خلف ميزة خاضعة للتحقق وتجربة بيئة معزولة، وليس إلى حسابات إنتاجية قبل الموافقة والاختبار.
8. تحديث قائمة المواد مع ترقية أسماء العرض دون تغيير `sub:` IDs تلقائيًا؛ حفظ الأصل والاسم الرسمي والمرادفات والطبعة ومصدرها.

## ما نفذناه ضمن المرشح المعزول
- `src/lib/curriculum-context-v2.js` يقدم عقدًا نقيًا يُنشئ مسودة سياق، ويرفض التحويل غير المتطابق، ويمنع إسناد مادة إلى برنامج آخر أو حساب آخر، ويدعم رياض الأطفال والحضانة.
- `tests/curriculum-context-v2.test.mjs`: **23/23 اختبارات نجحت**.
- لا يُستدعى هذا العقد من واجهة ركيز الحالية؛ غير متصل بقاعدة البيانات أو REST أو Supabase. `writeAllowed=false` دائمًا.
- اختبارات الميزة القائمة: 22 وحدة اختيار، 5 تفاعل، 3 حفظ محلي اصطناعي؛ جميعها ناجحة. اختبارا Account fixture الأساسيان `OFFLINE_LEASE_LIMITED` تكررا على `main` النظيفة، ولا حاجة لتعطيل حماية Lease.

## شروط الإغلاق المنتج
- اسم رسمي مطابق للمصدر لكل صف/مسار/برنامج؛ علامات واضحة للأسماء الجزئية أو سنة النفاذ غير المثبتة.
- فصلان مختلفا البرنامج لا يتم دمجهما لمجرد تطابق الصف ورمز الفصل؛ لا يتكرر كشف طلاب الشعبة الصحيحة.
- انتقال بين جهازين وحسابين وOffline ثم العودة والتحقق من نسخة الاحتياط وإعادة الاسترجاع والأرشفة، من دون فقدان الروابط أو تغيّر درجات الطلاب.
- تقارير الحالة وإيصالات Sync وOwner وRLS واضحة. لا نعدّ الاختبار المحلي إثباتًا لنشر قاعدة البيانات.
