# Rakeez continuous controller

Operational reference for the installed continuous delivery dispatcher under the Product Owner's 2026-10-12 authorization. The controller manages explicitly activated work; current assignments, blockers and receipts belong in the live runtime files. Product contracts, exact data permissions and actual PO acceptance remain authoritative.

## Components and configuration

`controller.mjs`, `worker-broker.mjs`, `run-task.ps1`, `start-ops.ps1` and `resource-lease.ps1` live directly in `scripts/ops-supervisor-v4/`. The sibling components `publisher.mjs`, `product-records.mjs` and `worker-policy.txt` also belong in that directory; the controller imports the two modules there by default. The former supervisor/refill/director entrypoints are retired. Keep one dispatcher and preserve unrelated scripts and historical evidence.

Runtime remains `artifacts/ops-supervisor-v4/`, containing `workflow-v5.json`, `intake-catalog.json` and `queue/*.json`. Completed historical cards are retained without replay. Each newly authorized catalog card has the same explicit `activationId` as `workflow-v5.json.controller.activationId`; only those cards are admitted. Append further eligible cards under the same activation to continue the backlog without a chat message, scheduler restart or another planner. Admission rechecks the canonical Product ledger and honors actual CLOSED/DEFERRED states.

The config remains version 5. `maxWorkers` is the live capacity field: use `1` while qualifying an affected runtime change, and `2` for independent eligible scopes once that change is verified. The controller rereads it every tick; the actual configured value is in runtime, not this document. `controller` holds `activationId`, `codexPath` and the repository/provider paths. The example files document the card interface; adopt a specific authorized card rather than replacing an existing runtime wholesale.

The single `RAKEEZ-Continuous-Delivery` scheduled task calls `start-ops.ps1` and waits for Node. Its sibling installer maintains the task under Abody's interactive account, with AtLogon/recovery triggers, one instance and no execution time limit. The launcher and child script invocations use process-scoped `RemoteSigned`: at cutover this machine had the default `Restricted` policy and no MachinePolicy/UserPolicy set. This preserves global and managed policy settings. Automatic execution requires the user's logged-in session; it does not promise work before logon.

## State and recovery

The controller is the sole writer of queue state. The wrapper writes only one attempt checkpoint, stdout JSONL, stderr and the structured final response. The published receipt belongs to the deterministic publisher. `ACTIVE_TASKS.json` is a current summary and `controller-events.jsonl` is the transition journal; the process inventory and birth identity determine actual liveness.

In the observed Windows PowerShell 5.1 Scheduler context, a direct detached PowerShell launch exited zero without executing its command. A non-detached launch entered the script, but did not survive its Node parent's exit in the tested case. The controller therefore starts one small detached Node `worker-broker.mjs` per attempt. The broker starts the existing PowerShell wrapper without detaching it and stays alive until it exits; queue decisions and retries remain with the controller. A native Scheduler fixture proved that the wrapper completed four seconds after the initiating Node parent exited. This is a bounded startup/lifetime result, not a long-duration availability claim.

Startup files are `broker.stdout.txt`, `broker.stderr.txt`, `wrapper.stdout.txt`, `wrapper.stderr.txt`, and `wrapper-launch.json`. The launch receipt records the actual wrapper executable, arguments, working directory, exit code and signal, even if PowerShell exits before its first checkpoint. Directly inherited file handles retain output across controller restarts. These are separate from Codex's `events.jsonl` and `stderr.txt`. Broker identity uses the unique task/attempt invocation plus observed PID and birth time; its descendants participate in existing adoption, watchdog and absence checks. An older running attempt without a broker is adopted through its existing checkpoint as before.

`pending → running → delivery → awaiting_po` is the normal path. `awaiting_po` releases the execution slot and does not mark Product CLOSED. The records helper updates the existing Product status/PO review block while preserving the user's notes. A later actual entry in the Closed Product ledger can change the runtime to `closed`. Record write failure never retries the model or publisher; the same record transition is retried independently.

Each launch has an immutable attempt specification and a UUID run ID. Codex's `thread.started.thread_id` is saved as the exact session ID in its checkpoint and queue record. Resume passes that ID explicitly, never `--last`, and preserves the existing worktree and candidate. A restarted controller adopts a living wrapper or Codex child only after matching its PID, birth time and invocation. It waits for owned descendants as well. PID reuse does not make an unrelated process an owner. If process inventory is unavailable, the controller writes the issue and starts no additional worker.

Quota/auth/network failures keep the session/worktree and use durable backoff. Quota/auth backoff starts at 15 minutes and is bounded at 60 minutes; network backoff starts at 15 seconds and is bounded at 5 minutes. These are local retry choices, not claims about OpenAI limit reset times. Only one saved-session probe runs while a shared model outage is active. They do not consume the two implementation-failure attempts. Two actual implementation failures park that card and leave independent cards eligible.

A running wrapper owns its temporary browser/integration/live resource through the existing lease path. During delivery, the owner is the controller's verified identity. A prior controller's integration lease can be reclaimed only for the same activated task after the exact former process is absent. An ended worker's phase lease can be reaped only for that same activation/task/run, with a saved controller absence record that includes its exact owner and known descendants, followed by another native process-identity check. The reaper itself requires the verified live controller. Unknown legacy leases remain recorded. A pending provider receipt holds the one delivery lane so a later push cannot overtake its production observation. On controller restart, only the publisher journal is resumed, with no new Codex worker for an already prepared candidate.

Cards explicitly marked `executionMode: local` or `synthetic` can use `budgetMinutes` and `idleMinutes`. A useful-progress clock tracks JSON events and content fingerprints of scoped files/Git HEAD; a wrapper heartbeat alone does not reset it. For the first cards, N92 is 20 minutes total/8 minutes idle and N91 is 45/15. On an expired budget, the controller first saves the exact owned process identities, then stops only matching PID/birth identities and their observed descendants, waits for a fresh absence check, and resumes the saved session once. A second implementation/watchdog failure parks the card. Any `liveAuthorizationRef`, live-mutation resource or live execution mode disables this automatic interruption. A malformed checkpoint becomes a specific incident; it cannot trap an ended worker in `running` forever.

`STOP` or `STOP-REFILL` pauses admission, worker and publication starts while the controller remains alive and refreshes its summary. A later explicit resume permits removal of the matching pause marker, after which the controller continues automatically. The historical 2026-10-12 08:54 hold was superseded by the 11:44 execution authorization; any newer stop remains binding.

## Permissions and trusted completion

Fresh execution uses `codex exec --sandbox danger-full-access -c approval_policy=never`. Resume uses the installed command's supported `-c sandbox_mode=danger-full-access -c approval_policy=never`, with `ProcessStartInfo.WorkingDirectory` and the exact session positional argument. A read-only attempt stays read-only. `--approve-for-me` is absent because this installed CLI selects workspace-write for that option.

PowerShell 5.1 compatibility matters: prompt input is explicitly UTF-8 bytes through `StandardInput.BaseStream`; this .NET runtime lacks `StandardInputEncoding`. Atomic checkpoint replacement uses `[NullString]::Value`, because `$null` was converted to an invalid empty backup filename in the native probe. stdout/stderr files allow concurrent reads. All argv values are quoted using Windows argv rules; prompts are not shell commands.

Lease process identity must preserve full creation-time precision across PowerShell versions. PowerShell 7 can deserialize a JSON timestamp directly as `DateTime`; passing that value through `DateTime.Parse` first converts it to a string and can lose fractional seconds/timezone information. The direct `[DateTime]` cast preserves the existing value before conversion to UTC ticks. Keep the exact PID/birth/invocation checks; correcting timestamp conversion does not relax ownership verification.

The required final response is the schema saved at runtime in `worker-result.schema.json`: task/run identity, `LOCAL_READY | BLOCKED | NO_CHANGE`, full candidate/base SHA, worktree, changed paths, scoped checks and blocker details. A model's final message alone cannot mark production. The controller checks the actual Git HEAD, declared-base ancestry, tracked cleanliness and the approved path scope before delivery. Every name in a card's `requiredChecks` must have a corresponding `PASS` entry; `NOT_RUN` does not satisfy it. This validates the existing affected-check receipt, without rerunning the check. The first cards use `scope`/`syntax` and `responsive_layout`/`card_navigation`, respectively.

The publisher owns integration/current-main checks, deterministic metadata/build, non-forced push, provider observation and served-source verification. FAST copy work uses the publisher's metadata-only path; STANDARD uses its single integration build. A worker's text `PASS` is not passed as a trusted build-cache key. Build/merge failures are returned as bounded correction context to the same original Codex worktree/session; the integration worktree is diagnostic context, not a replacement candidate identity.

`awaiting_po` requires the host publisher's candidate-to-published ancestry, exact provider head/deployment, verified immutable and Production assets, and a changed Product source asset. Production metadata currently contains a content fingerprint, not a Git SHA. The observer compares actual source bytes. The only allowed normalization is the tested, narrowly matched Cloudflare JSD insertion in HTTP-200 `index.html`; it retains the raw hash and also proves the normalized hash equals the expected Git blob. A generic HTML cleanup is not accepted.

Publication receipts in these tests are synthetic; the suite makes no real publication or Product data mutation.

Recorded native evidence on 2026-10-12 is separate from that suite:

- The Scheduler/bootstrap fixture reproduced the original PowerShell startup failure and demonstrated broker-backed wrapper completion after the initiating parent exited. That fixture used no Codex or Product changes; its processes and temporary task were cleaned up.
- Native lease checks passed **8/8** after correcting the PowerShell timestamp conversion described above. The correction preserves exact owner identity rather than weakening the check.
- N92 completed a real worker run and reached verified Production SHA `3eb897dc9fdc760ee035156ca681f02bfab8d979`, with successful provider identity and 4/4 immutable plus 4/4 Production source checks. Its recorded state is `awaiting_po`, not Product CLOSED.
- Scheduler started the next real N91 Codex session and it saved a candidate. Its later browser-lease timestamp incident is a distinct process-identity issue, not a failure to start Codex. Read the current queue/result for its latest disposition rather than treating this historical checkpoint as current status.

These receipts prove the specified startup, resume and publication cases. They do not constitute a 24/7 soak, physical-device acceptance or automatic Product closure. Check additional scenarios only when the affected behavior requires them. Current evidence is under `artifacts/ops-supervisor-v4/{attempts,results,delivery}` and `controller-events.jsonl`.

The controller does not automatically resolve a real Product/data authorization blocker, delete unknown leases, buy extra quota, reset a worktree, force-push main or claim real-device/user acceptance. Those conditions are kept on the affected card, while routine PM handoffs and waiting for the chat are removed from execution.
